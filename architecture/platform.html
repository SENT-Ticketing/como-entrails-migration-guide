Platform answer

What OPN already gives
the migration

OPN can take responsibility for the ordinary ticketing business: catalogue, pricing, inventory, checkout, payment, ticket ownership, refunds, dashboard work and scanning. It should remain the commercial system of record even when an Italian issuer service is added beside it.

Read this page when you need to judge whether a proposed feature belongs in Entrails, an existing adapter, or a new issuer service. You can skip the full platform architecture unless you need code-level evidence or the API and async model.

01

Why the model is useful

OPN separates the thing a fan owns from the right that gets them through the gate. That gives the migration a sound commercial core.

Ticket

The ownership record. It carries the sale, transfer and resale lifecycle.

→
Privilege

The actual right of entry. Check-in, seat allocation and ticket-engine records attach here.

→
Seating

The selected or allocated place for that privilege, when the event uses seating.

This separation means the target does not need a special ticket type for every commercial workflow. A subscription, invitation, transfer or resale can use the same commercial records while the entry right, seat and issuer evidence follow their own lifecycle.

Inventory is shared through pools

Ticket kinds sell access to privilege-type inventory. A combined ticket is available only while every required pool has capacity.

Money has its own record

Orders, payments, refunds, payouts and ledger transactions stay separate from a ticket's ownership state.

Tenancy is deliberate

Ticketeer, organization and event form the scope hierarchy. Users are global and access is applied through roles and query scoping.

One known limit

Scanning records a current checked-in state, not a complete scan journal. Regulated access reporting needs that additional evidence layer.

02

Why the sales path is safer than the current Como pattern

The critical transaction keeps payment, ticket ownership and accounting together.

Cart

Adding a ticket reserves inventory. A periodic cleanup releases expired carts and orders.

→
Order completion

The payment row is locked while ownership transitions and ledger rows are written in one PostgreSQL transaction.

→
Outbox

The ticket-engine record is queued as a local row and sent later. A remote engine call does not sit inside the sale.

What this means for the migration

Do not reproduce the current dependency where payment succeeds and a remote title call can leave the order in an indeterminate state. The issuer integration should receive a durable request after the commercial sale is committed, then report its own result back to OPN.

03

What this does not solve

Some requirements fit existing seams. Others change the target architecture.

Good extension seams

  • New sellable products can use the existing ticket kind and privilege model.
  • Payment methods are adapter-based.
  • Delivery and notifications can be replaced behind their integrations.
  • Events, pricing, seats, reservations and organisation roles already have operating surfaces.

Requirements that change the design

  • A named legal holder and fiscal evidence are not ordinary profile fields.
  • Italian fiscal title lifecycle and C1/C2 reporting need an issuer record and append-only evidence.
  • Consumer click-to-pick seating is not the current shop experience.
  • White-label brands are separate static builds, not runtime theme switches.
