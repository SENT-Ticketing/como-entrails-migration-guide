Repository and architecture assessment

Reuse Engine Open.
Do not deploy it unchanged.

SENT has forked GETProtocol's public Engine Open repository. This study tests whether its existing Entrails-facing API, durable action model, workers, status queries, and callbacks can become the foundation of the Italian certified issuance service.

DecisionAdopt as a controlled foundation

Keep the Go repository and its useful integration patterns. Carve out a small fiscal service with a new data model and contract. Remove blockchain-only execution from the Italian deployment instead of renaming it.

01

The short answer

The repository fits the integration problem better than it fits the regulated domain.

Keep

The foundation

  • Go repository and source provenance
  • tenant API authentication concept
  • durable action + promise pattern
  • PostgreSQL system of record
  • async worker and status polling
  • persisted callbacks and recovery tasks
Replace

The execution model

  • server-only request identity
  • positional batch correlation
  • blockchain action states
  • unsigned sparse callbacks
  • mutable status as historical evidence
  • generic ticket actions as fiscal commands
Exclude from Italian runtime

The unrelated stack

  • chain cores and transaction assembly
  • broadcaster and confirmer services
  • wallets and gas/fuel accounting
  • NFT metadata and CDN invalidation
  • DynamoDB unless a new need is proven
  • Kafka until measured load requires it
Suitability conclusion

Engine Open is suitable as a code and contract foundation. It is not a configurable Italian issuer. The smallest safe adoption is one API process, one worker, and PostgreSQL, with Planet behind a normalized provider adapter first.

05

Contract Entrails should call

Capabilities remain stable while Planet is replaced behind the provider boundary.

POST /v1/fiscal-configurations

Version configuration

Event, sector, reduction, price/VAT, gate and subscription allocation facts. Activation makes used values immutable.

POST /v1/issuance-prechecks

Check readiness

Configuration, capacity, holder evidence, supporter/pre-emption and applicable Ve.R.O. decision.

POST /v1/issuance-requests

Request per-right issue

Client request and operation IDs, explicit idempotency, frozen buyer/holder/seat/price and independent results.

GET /v1/operations/{id}

Recover authority

Normalized current state and title links. Polling works if a callback or HTTP response was lost.

POST /v1/cancellation-requests

Append cancellation

Fiscal cancellation is separate from refund and inventory release.

POST /v1/holder-change-requests

Change named holder

Preserves certified-title continuity and Entrails commercial lineage separately.

POST /v1/reconciliation-runs

Compare facts

Operation, event, subscription, report, access event or migration batch. Observations are append-only.

Identity rule
Entrails order≠commercial ticket≠privilege≠ issuer operation≠certified title≠fiscal seal≠gate token

Each identifier is stable, explicit, and linked. None is inferred from array position.

Failure semantics

accepted→precheck pending→ready→submitting→issued
Alternaterejectedretry waitoutcome unknownoperator reviewcancelledsuperseded
A timeout is not a failure.

If Planet may have accepted the request, the operation becomes outcome_unknown. The worker performs an authoritative title lookup before it can retry. This rule prevents a second valid title.

07

Evidence needed next

The source audit narrows the questions; it does not invent private-system behavior.

Planet: idempotency and title recovery P0
  • What stable key deduplicates every mutating endpoint?
  • After a timeout, what lookup proves whether the title exists?
  • How long can provider replication make a lookup falsely negative?
  • Which error codes prove that no title was created?
  • Supply redacted success, rejection, duplicate, partial and timeout scenarios.
Planet: contract and operating context P0/P1
  • Which exact Ticka/PlaNet version runs in production and test for Como?
  • Supply the versioned OpenAPI or equivalent contract for every endpoint Como calls.
  • Are the primary and fallback endpoints one logical system, and is alternating them safe for mutating retries?
  • Define token lifetime, rotation, concurrency, clock tolerance and environment separation.
  • Is session_id tracing only, or does it carry a deduplication guarantee?
  • Return the supported endpoint inventory, and name every mutating endpoint required for cancellation, correction or report recovery that Como does not currently call.
Planet: lifecycle, season and reports P0/P1
  • Versioned schemas for all match/season issue variants and fields.
  • Which fields are legally or certification required, versus Planet implementation choices?
  • Full title state machine, cancellation/correction, and Cessione identity continuity.
  • Season collection/log semantics and per-event rateo calculation.
  • C1/C2 schemas, signing, receipts, rejection and correction examples.
  • Stable per-endpoint error catalogues stating retryability and whether a title may exist.
Recognition and activation card P0
  • What exact frontend, API, device and access components are inside the approved perimeter?
  • Can a cloud API and Italian card agent form one recognized system?
  • Can one SENT operator serve multiple clubs, and what repeats per deployment?
  • Which software/configuration changes require a new variant or evidence cycle?
  • Does producing a new certified system require approval on both the Agenzia delle Entrate/SIAE track and the Interior Ministry track, and in what sequence and lead time?
  • Which configuration facts become immutable after first title or report use, and what is the lawful correction path for each?
  • Confirm complimentary thresholds, dynamic-VAT formula, precision and effective-date source.
Ve.R.O., Questura and holder eligibility P0
  • Who holds the authorized Ve.R.O. connection today — Planet, Como or SENT Italy — and is that authorization transferable to a new producer?
  • Is the eligibility decision inside or outside the issuance transaction? A Questura timeout would otherwise become a second source of unknown outcome, alongside Planet.
  • Supply the production and test interface contract, authentication and network requirements.
  • Which event, sector, product and holder scenarios require a decision, and which policy source controls it?
  • Define request fields, normalization, matching and the result vocabulary.
  • Define decision validity window: must it repeat at issue, holder change and entry?
  • Define timeout and unavailable behavior: block, retry, operator exception or another procedure.
  • Which protocol generation is live for Como? An internal SENT brief asserts “VRO 2.0” without a source; treat as unverified until confirmed.
Outage, continuity and correction P0/P1
  • What issuance, gate admission and reporting fallback is permitted during network, card, authority or backend outage?
  • What maximum offline periods, queues and reconciliation deadlines apply?
  • Which clocks must be synchronized, and what drift is tolerated?
  • What disaster-recovery, backup/restore and tamper-detection evidence is required?
  • Define report rejection handling: resubmit, correct, replace, and how sequence continuity is preserved.
Alfi live access interface P0
  • Who owns barcode/token creation, valid-title lists and canonical scan history?
  • What is the live protocol, identifier set, acknowledgement and replay behavior?
  • How do issue, cancellation, holder/seat change and season rights reach every gate?
  • How do offline devices synchronize and how is event opening reconciled?
  • What test plan and evidence does the mandatory ticketing/access-control integration require, and which exact builds are named in the accepted one?
  • Can another venue provider implement a normalized adapter, or does each need a separately approved integration path?
Como scope and operations P0/P1
  • Approve first-cutover versus legacy-shutdown capabilities.
  • Choose seat/capacity authority for every coexistence phase.
  • Supply failed issue, partial issue, backlog, cancellation, report and outage runbooks.
  • Confirm volumes, SLAs, roles and 24/7 incident ownership.
Security, privacy and records P0/P1
  • Classify purchaser/holder/provider/report/access fields and retention.
  • Define protected raw-evidence storage, masking and break-glass access.
  • Define audit/tamper evidence and key/card custody.
  • Confirm whether seals, barcodes and provider IDs are security-sensitive.
Engine Open adoption P0/P1
  • Confirm licence and attribution obligations, and whether required private runtime components are available or intentionally excluded.
  • Is the public repository the production source wired to Entrails today, or a partial distribution?
  • Name the owner, maintainer and supported branch policy for the SENT fork, and the fork-synchronization end date.
  • Supply the deployed Entrails-to-engine API version and known contract differences from public main.
  • Approve the minimal Italian topology — API, worker and PostgreSQL — or give a measured reason Kafka and DynamoDB are required.
  • Does any downstream client besides Entrails require /stream compatibility?
Best next deliverable

One coherent redacted match and season scenario pack: Como order/payment, requested rights, Planet requests/results/title/seal, C1/C2 references, Alfi entitlement/scans, lifecycle changes, failures and recovery. Consistent fake IDs are more valuable than isolated screenshots.
