Technical discussion note

Como to Entrails ticketing migration

This note compares the current Como platform with Entrails. It focuses on the data model, Italian ticketing requirements, and the work that would be needed to move the Como flows into Entrails.

Working assumption

Entrails is the intended target platform. Como and Ticka/PlaNet would continue to support existing flows during migration, especially season tickets. The cutover sequence and the scope of a SENT-owned fiscal component are still open for discussion.

System boundaries

The proposed side is a working architecture. It still depends on certification and integration decisions.

What the Planet adapter currently covers

The inspected adapter is about 4,100 lines, excluding the separate match and season issuance flows. A direct API rewrite would move several current couplings into Entrails. The responsibilities should be split first.

AreaCurrent useLikely target placement
Events and code tablesOrganizers, events, seat orders, reductions, subscription typesEntrails configuration, with certified codes referenced by the fiscal component

Gaps that affect the target model

AreaMissing or different in EntrailsWhy it mattersPriority
Person rolesPurchaser, operator, commercial owner, named holder, and attendee are not represented separately at issuance time.A mutable owner or profile cannot stand in for the person named on a title.Before pilot
Fiscal configurationNo versioned seat order, reduction, and price or tax snapshot for each issued right.Later configuration edits must not change historical fiscal evidence.Before pilot
Certified title identityThe fiscal title, seal, barcode, Ticket ID, and Privilege ID need separate fields and links.They have different purposes and lifecycles.Before pilot
SubscriptionsNo explicit season instance with included events, seats, value allocation, and rateo.A season title cannot be treated as one ordinary ticket or product bundle.Before season migration
Issuance recoveryNo per-right state for partial success, retry, cancellation, correction, and reconciliation.A paid order can contain a mix of successful and failed external issuances.Before pilot
Inventory authorityPlanet, Firestore, and Como currently hold related seat state.One system must approve each capacity write during migration.Before data import
Access historyPrivilege.claimed is a current state, not a scan journal.Repeated attempts, denials, reversals, and device context cannot be reconstructed from a Boolean.Before gate integration
Migration lineageNo general mapping ledger for source IDs, target IDs, checksums, runs, and corrections.Imported records must remain traceable after Como is no longer available.Before data import

Current implementation patterns not to carry over

  • Direct client writes for privileged transitions
  • Position-based matching of seats, holders, and provider responses
  • Mutable report documents used as historical evidence
  • Process-local enforcement of capacity or purchase limits
  • Authorization scope enforced only by client filtering
  • Raw Planet responses used as the application data model
  • Separate match and season implementations with duplicated rules
  • Repair jobs that overwrite the record they are meant to reconcile

Items that still need a current source or sample

  • The accepted C1 and C2 schemas, examples, transmission responses, and correction process.
  • The exact source, event scope, and effective date for the reported Codice Fiscale or accreditation change.
  • The current retention rules for football holder data and their relationship to fiscal record retention.
  • The certification perimeter for the online shop and the Alfi access integration.
05

Transition outline

The sequence below is a discussion basis. Dates depend on the certification work and existing season-ticket obligations.

1Current service

Como and Ticka remain authoritative.

→
2Evidence and design

Confirm specifications, ownership, and certification path.

→
3Single-match pilot

Run one representative event and reconcile all results.

→
4Dual servicing

New flows move while existing season rights remain supported.

→
5Legacy exit

Retire only after reporting, correction, access, and rollback checks pass.

The suggested pilot includes seated and standing inventory, one reduction, complimentary issuance, named holders, cancellation, and refund handling. Reconciliation should cover money, capacity, issued titles, holders, and access results.

06

Decisions and evidence owners

These are the questions that should leave the meeting with an owner.

  1. 01

    Confirm the intended end state and the legacy servicing obligations that remain during migration.

  2. 02

    Obtain the current Ticka recognition dossier, approved version, operating procedures, and interface contract.

  3. 03

    Obtain the current transaction log and transmission specifications, a test card, and accepted examples.

  4. 04

    Identify the conformity or certification partner and confirm the system components included in review.

  5. 05

    Confirm the Questura or VRO process, the accreditation requirement, and the Alfi contract boundary.

  6. 06

    Approve the minimum holder data, access controls, retention, correction, and deletion policy.

  7. 07

    Agree which system owns inventory during import, pilot, and dual servicing.

  8. 08

    Define the reconciliation and exit checks for retiring each legacy responsibility.
